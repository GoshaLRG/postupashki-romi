# Поступашки: куда исчезает маркетинг

Measurement system для проекта, где фиксируется только факт оплаты,
а маркетинговые касания исторически не логировались.

Репозиторий содержит **блок 1** решения: очистку слоя продаж и
восстановление маркетингового календаря из самих продаж — без доступа
к каналу и без журнала размещений.

## Быстрый старт

```bash
pip install -r requirements.txt
python run_analysis.py
```

Скрипт читает `data/raw/base.xlsx` и кладёт результаты в `output/`.
Внешняя сеть не нужна, всё считается локально за секунды.

## Что делает пайплайн

```
base.xlsx
   │
   ├─ src/prep.py            строки → заказы, прайс-цены, индекс скидки

   └─ src/charts.py          графики для презентации

```

## Три уровня знания

Решение явно разделяет то, что мы знаем, оцениваем и не можем узнать.

| Уровень | Где в репозитории | Пример |
|---|---|---|
| **Знаем** | `orders.csv`, `daily_metrics.csv` | 628 заказов, 606 покупателей, 5,9 млн руб. выручки |
| **Оцениваем** | `campaign_calendar.csv` (`knowledge_level = estimated`) | 08–12.08 была распродажа со скидкой ~45%, давшая +121 заказ к baseline |
| **Узнать нельзя** | раздел ниже | из какого канала пришёл покупатель и сколько стоило размещение |

## Assumptions (принятые решения по неоднозначным данным)

1. **Заказ** = `student_id` + timestamp, совпадающий до секунды. Обоснование:
   доступ к курсу выдаётся в момент оплаты, поэтому одинаковая секунда
   у одного покупателя — одна транзакция. 795 строк → 628 заказов.
2. **Уникальный покупатель** = `student_id`. Один человек с двумя
   Telegram-аккаунтами будет посчитан дважды — это принимаемая погрешность.
3. **Прайс-цена курса** = 90-й перцентиль сумм по *одиночным* заказам,
   после отбрасывания строк дороже 11 000 руб. (сетка цен курсов —
   6 450–9 950 руб., всё выше в одиночном заказе — пакетная сумма
   в одной строке). Отсюда считается `discount = 1 − amount / list_price`.
4. **Пакеты.** В данных встречаются оба варианта: пакет, разложенный на
   строки по равной доле (заказ на 9 990 = две строки по 4 995), и заказ
   из 5 курсов, где каждая строка стоит полную цену. Разделить их
   однозначно нельзя, поэтому выручка считается суммой строк заказа,
   а факт неоднозначности фиксируется как ограничение оценки сверху.
5. **Последний день выгрузки (10.09)** обрезан — данные только до 06:09,
   поэтому он исключён из временных рядов.
6. **Левая цензура.** История начинается 04.08. Курсы, впервые проданные
   в первые два дня, запусками не считаются: они наверняка продавались
   и раньше.

## Метод восстановления календаря

Журнала размещений нет, но кампания оставляет след в продажах:

- **Всплеск объёма.** `baseline` = медиана заказов за предыдущие 14 дней.
  Медиана по длинному окну устойчива: 2–3 дня всплеска внутри окна её
  почти не двигают, поэтому кампания не «съедает» собственный baseline.
  Событие: заказов ≥ 2× baseline и ≥ +5 заказов в абсолюте.
- **Провал цены.** Медианная скидка дня ≥ 20% от прайса → скидочная акция.
- **Новый продукт.** Первая продажа курса + ≥ 3 продажи за 7 дней → запуск.
- Соседние окна, разделённые одним спокойным днём, склеиваются.

Классификация окна:

| Сигналы | Тип события |
|---|---|
| всплеск + скидка | `sale` — распродажа |
| всплеск + новый курс | `product_launch` — запуск |
| всплеск без скидки | `traffic_spike` — кандидат на внешнюю рекламу или продающий пост |
| скидка без роста объёма | `targeted_promo` — точечные промокоды |

**Про сезонность.** Мы проверили профиль дня недели вне детектированных
окон: устойчивого эффекта нет, выходные не выше будних. Все три волны
пришлись на выходные не потому, что это сезонность, а потому что на
выходные ставили кампании. Поэтому сезонная поправка в baseline
намеренно не вводится — иначе всплеск кампании растворился бы
в «нормальной субботе».

## Ограничения метода (честно)

- Календарь — **оценка, а не факт**: мы видим след кампании, но не её
  причину. Всплеск без скидки может быть и рекламой у блогера,
  и попаданием в рекомендации, и внешним инфоповодом.
- 38 дней истории и 4 события — статистики для разделения эффектов
  канала, креатива и скидки категорически не хватает.
- `incremental_revenue_est` — разница «факт минус baseline», то есть
  верхняя оценка эффекта. Часть этих продаж случилась бы и без рекламы
  (каннибализация будущего спроса скидкой). Корректная оценка требует
  holdout-дизайна, который система должна начать собирать.
