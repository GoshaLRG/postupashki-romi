# Трекинг внешней рекламы

Слой, которого у бизнеса нет вообще: связь между рекламным размещением
и конкретной оплатой. Без него ROMI не считается ни при какой модели
атрибуции.

## Запуск за минуту

```bash
python tracking/links.py       # создать размещения и диплинки
python tracking/simulate.py    # прогнать синтетический трафик
python tracking/report.py      # воронка в разрезе размещений
```

Токен и сеть не нужны: эмулятор вызывает тот же код записи событий,
что и боевой бот.

Боевой режим:

```bash
pip install aiogram
export BOT_TOKEN=...            # токен от @BotFather
export TRACKING_SALT=...        # соль для хеширования, НЕ в репозиторий
python tracking/bot.py
```

## Архитектура

```
channels.csv
     │
     ▼
links.py ──► ad_registry          placement_id, cost, publication_time
     │        + deep_link         https://t.me/Bot?start=c01_p01_cr2
     │
     ▼  ссылка уходит в рекламный пост
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
    bot.py                  simulate.py
    (боевой)                (демонстрация)
        └────────────┬────────────┘
                     ▼
                  core.py           ◄── единственная точка записи
                     │
                     ▼
        touch → lead → payment      SQLite, tracking.db
                     │
                     ▼
                 report.py          воронка по размещениям
```

**Почему логика вынесена в `core.py`.** Бот нельзя протестировать без
токена, интернета и живых пользователей, а на защите это означает
«у нас всё работает, поверьте». Здесь и бот, и эмулятор вызывают одни
и те же функции записи, поэтому проверка эмулятором — это проверка
боевого кода, а не его имитации.

## Идентификаторы

Метка передаётся через deep link Telegram: `t.me/Bot?start=<payload>`.
Формат payload — `c{канал}_p{размещение}_cr{креатив}`, например
`c01_p01_cr2`. Три уровня различаются независимо, поэтому можно
сравнивать не только каналы между собой, но и креативы внутри одного
размещения.

Пользователь связывается между системами анонимным ключом:

```
user_hash = SHA256(telegram_user_id + соль)
```

Ни username, ни имя, ни телефон в хранилище не попадают. Соль живёт
в переменной окружения. Выданный в кейсе `student_id` устроен так же,
поэтому исторический слой оплат стыкуется с новой схемой.

## Правила, зашитые в код

| Правило | Где | Зачем |
|---|---|---|
| Размещение без `cost` или `publication_time` помечается неизмеримым | `links.py`, `report.py` | иначе ROMI считать не из чего, и лучше знать об этом заранее |
| Стоимость слота делится между креативами | `links.py` | один оплаченный слот, показанный по-разному, не должен считаться дважды |
| Payload не разобрался → `placement_id = NULL` | `core.py` | органика остаётся органикой, а не приписывается каналу |
| Метка есть, а размещения в журнале нет → `campaign_id = UNREGISTERED` | `core.py` | видно, что ссылка гуляет вне учёта |
| Оплата без касания в окне не распределяется между каналами | `report.py` | доля неизвестного — метрика качества, а не повод для догадок |

## Данные

| Источник | Пометка | Что это |
|---|---|---|
| `base.xlsx` | реальные | 795 строк оплат, выданные в кейсе |
| `tracking.db` | `is_synthetic = 1` | касания, лиды и оплаты, созданные эмулятором |

Смешивать их в одном расчёте нельзя: синтетика показывает, что система
работает, а не сколько заработал бизнес.

## Что показывает демонстрация

На сгенерированном трафике сразу видно то, ради чего система строится:
канал с самым дешёвым и самым объёмным трафиком даёт почти ноль оплат,
а канал втрое дороже за переход окупается лучше. По количеству
переходов эти каналы не различить — только по сквозной воронке.

## Чего этот модуль не делает

Сравнение моделей атрибуции и расчёт ROMI — блок 3. Здесь атрибуция
намеренно простейшая (last touch), потому что задача модуля — довести
данные до состояния, в котором атрибуцию вообще можно применять.
